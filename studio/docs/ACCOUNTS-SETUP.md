# Личные кабинеты: логины и пароли

04.10.2026. Пользователь выбрал аккаунты, которые создаёт администратор. SMTP и электронная почта для входа не нужны. Это инструкция к реализации, не подтверждение внешнего размещения.

## Возможности

Менеджер сохраняет/открывает свои проекты, историю, архив и библиотеку. Администратор видит все проекты, создаёт аккаунты менеджеров/администраторов, задаёт новые пароли и отключает доступ. Чужой проект сохраняется своей копией. Пароль можно изменить самостоятельно с вводом прежнего; остальные сессии завершаются. При административном сбросе или отключении завершаются все сессии сотрудника. Самого себя отключить нельзя.

Открытой регистрации, общих встроенных паролей и почтового входа нет. Сохранение проекта пока ручное; проверка revision и история сохранены. Облачное автосохранение — следующий этап.

## Первый администратор

Python 3.12+, зависимости `server/studio-requirements.txt`. На VPS использовать venv; локально также поддерживается `server/.studio-deps`. Из корня репозитория:

```text
python server/manage_studio_users.py create --login admin --name "Администратор" --role admin
```

Пароль вводится дважды скрыто, не передаётся аргументом команды и не записывается в журнал. Длина 15–128 символов, допустимы фразы с пробелами. Логин: латиница/цифры/точка/дефис/подчёркивание, 3–64 символа, без различия регистра. Отображаемое имя может быть русским.

Дальше: «Кабинет → Сотрудники и доступ». Пароль для передачи сотруднику сохранить до отправки формы: после создания он больше не отображается. Восстановление доступа администратора локально на сервере:

```text
python server/manage_studio_users.py reset-password --login admin
python server/manage_studio_users.py list
```

База определяется `STUDIO_DB` либо `--db`; сервер и команды должны использовать один путь. Команда create не перезаписывает существующий логин.

## Старые проекты

Перед переходом резервировать БД. Прежний email внутри проектов/истории/библиотеки остаётся постоянным ключом владельца. Новые аккаунты получают случайный ключ `user:…`. Имя поля API `email` сохранено ради совместимости, обязательной почты за ним нет. В UI показываются имя и логин.

Привязка прежних проектов выполняется явно локальной командой администратора:

```text
python server/manage_studio_users.py create --login manager1 --name "Менеджер" --role manager --legacy-email old@example.test
```

Из браузера присвоить чужой прежний email нельзя. Создание отзовёт старые сессии, но сохранит проекты, ревизии и библиотеку. `/auth/code` и `/auth/verify` удалены. SMTP, STUDIO_USERS, STUDIO_ADMINS, STUDIO_OPEN_SIGNUP больше не дают права входа.

## Запуск и размещение

`START-3D.bat`: интерфейс127.0.0.1:8103, API127.0.0.1:8104. `STUDIO_DEMO=1` разрешает HTTP только на loopback; даже локально нужны созданные аккаунты. Это не режим для сети менеджеров. При необходимости задать `STUDIO_PYTHON`. База по умолчанию `server/studio-data.db`, вне Git; прежний server/app.py не используется.

Для пилота без рендеров и локального ИИ ориентир 2vCPU/4ГБ RAM/SSD от40ГБ; это оценка для подбора, не проверенная нагрузочная ёмкость. GPU не нужен.

Linux VPS: отдельный непривилегированный пользователь, venv, systemd с перезапуском, HTTPS reverse proxy. Интерфейс и API на одном origin. Переменные:

```text
STUDIO_DEMO=0
STUDIO_SERVE_WEB=1
STUDIO_DB=/var/lib/furniture-studio/studio-data.db
STUDIO_ORIGIN=https://YOUR-DOMAIN
STUDIO_PORT=8104
```

Заменить YOUR-DOMAIN реальным адресом. `python server/run_studio.py` слушает только127.0.0.1; снаружи доступен HTTPS proxy. Он передаёт запросы в приложение, которое раздаёт `/studio/`, `/assets/tex/`, `/api/studio`; корень перенаправляется в `/studio/`. Не публиковать частные local-projects, тестовые базы и `.studio-preview`. На proxy ограничить размер/частоту запросов; доверять forwarded-заголовкам только от собственного proxy. Немецкий VPS не гарантирует доступность API ИИ для компании; условия поставщика проверяются отдельно.

## Хранение паролей и резервные копии

Пароли хранятся как scrypt с уникальной солью, N=131072,r=8,p=1; два одновременных хеширования на процесс. Вход ограничен 10 попытками/логин и50/IP за15мин; состояние переживает рестарт. Неизвестный, отключённый аккаунт и неверный пароль возвращают одинаковую ошибку. Cookie: HttpOnly, SameSite=Strict, Secure вне локального режима,7дней. Мутации проверяют origin и специальный заголовок. Ошибки валидации не отражают пароли.

`python server/backup_studio.py`: уникальная копия SQLite backup API и quick_check; поддерживает обе схемы. Копия содержит хеши и сессии, хранить закрыто. Не копировать только основной файл работающей WAL-базы. Внешнее хранение, расписание и пробное восстановление ещё нужно настроить; после восстановления отозвать сессии. История правок не заменяет резервную копию.

## Проверки

`python server/test_studio.py` — права, история, конфликты, backup, пароли, сброс/отключение, лимиты, CSRF, миграция. Браузерная приёмка: `studio/playwright.accounts.config.ts`, `studio/tests/accounts.spec.ts`, `STUDIO_PYTHON` с зависимостями. Заранее собрать Vite в `server/.studio-preview/studio` с copyPublicDir:false. Fixture использует временную БД и только loopback; её тестовые аккаунты никогда не переносить в рабочую БД.

Внешняя приёмка отдельно: HTTPS, вход с двух устройств, изоляция менеджеров, перезапуск и восстановление из внешней копии.
