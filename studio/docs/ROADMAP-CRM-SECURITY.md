## 1. Привязка к CRM (Google Apps Script, таблица = БД — таблицу не трогаем, только код)

Цель: из студии одной кнопкой создать заказ в CRM, без ручного перепечатывания.

- **Что передаём** (JSON `crm-order.v1`): номер замера/заказа, менеджер (из профиля), состав модулей (имя, Ш×В×Г,
  декор корпуса/фасадов, наполнение), смета (закупка, наценка/за лист, розница), листы ЛДСП по декорам, крепёж и
  фурнитура из `estimate().lines`, ссылка на проект в кабинете (`cloud.id`/`revision`), ZIP-комплект технолога
  (`reviewPackage`). Персональные данные клиента (ФИО, телефон, адрес) **в студии не хранятся** — их вводит менеджер уже
  в CRM; студия передаёт только номер замера.
- **Как**: кнопка «В CRM» в «Выдать документы» → `POST /api/studio/crm` на нашем FastAPI (`server/studio_app.py`) →
  сервер подписывает запрос секретом и вызывает веб-приложение GAS (`doPost`, действие `studio.import`). GAS создаёт
  строку заказа и возвращает `orderId`; студия сохраняет `project.crm={orderId, sentAt, revision}`.
- **Обратно**: статус заказа из CRM читается по `GET /api/studio/crm/{orderId}` (кэш 60 с, как в CRM-ускорении), чтобы
  в кабинете видеть «в производстве / собран / выдан».
- **Повторная отправка**: если `revision` проекта выросла — отправка обновляет заказ (GAS `studio.update`), старая
  смета остаётся в истории CRM.
- Шаги: (1) описать схему `crm-order.v1` в `docs/`; (2) в GAS добавить обработчик `studio.import/update/status` с
  проверкой подписи; (3) сервер: маршруты + тесты `test_studio.py`; (4) UI-кнопка и отметка в кабинете.

## 2. Профили и вход по коду на почту

Сейчас: `server/studio_app.py` — логин/пароль, `STUDIO_OPEN_SIGNUP`, библиотека шаблонов. План (как в «Просчитано»):

- Вход **кодом на почту**, без паролей: `POST /api/auth/request-code` → `verify` → сессия 90 дней (токен в
  httpOnly-cookie), лимиты 3/час и 10/сутки на адрес, 20/сутки с IP, коды — хэш sha256 с TTL 10 мин.
- **Роли**: менеджер (свои проекты, свои шаблоны), технолог (все проекты, комплекты, бирки), администратор (профили,
  цены, каталог). Роль задаётся администратором, самостоятельная регистрация — только по приглашению (домен почты цеха).
- **Профиль**: имя, роль, подпись в КП, свои ставки наценки по умолчанию, избранные декоры и ручки, библиотека модулей
  (уже есть `libraries`). Никаких данных клиентов в профиле.
- Почта: отдельный ящик сервиса с app-password, SMTP через stdlib; в DEV — `dev-outbox.log`.

## 3. Защита от копирования и от уязвимостей

Честная оценка: клиентский код (React + three.js) любой скачает — минификация и обфускация задерживают, но не
защищают. Защита — в том, чего нет в браузере, и в юридических мерах.

- **Ядро на сервере**: со временем перенести цены поставщиков (`pricing.ts` прайсы Lamarty/ФАМ/Лемана), правила цеха и
  раскрой в платный API; клиенту отдавать только результат. Публичная версия на GitHub Pages — демонстрационная,
  с ограничением функций (без цен закупки, без ZIP технологу).
- **Лицензия**: репозиторий сделать приватным или поставить проприетарную лицензию (сейчас public — код открыт
  де-факто); в подвале — «© Фабрика …, все права защищены», условия использования.
- **Технические меры для сайта** (чек-лист перед публичным доменом):
  - HTTPS, HSTS; заголовки CSP (`default-src 'self'`; шрифты — self после переноса Golos Text в `public/fonts`), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`.
  - Все входные данные проходят `parseProject`/`projectErrors` — уже строго; на сервере — размер тела ≤ 2 МБ, JSON-схема, лимиты частоты запросов, аудит-лог.
  - Cookie httpOnly + SameSite=Lax, CSRF-токен на изменяющие запросы, ротация сессий, выход со всех устройств.
  - SQLite: параметризованные запросы (уже), бэкап по cron, WAL, один воркер.
  - Экспортные HTML (КП, ведомость, бирки) — весь текст через `esc()`; в предпросмотре — `iframe sandbox=""` (уже так).
  - Зависимости: `npm audit` в CI, фиксированные версии, обновление раз в квартал.
  - Внешний пентест перед выходом за пределы цеха; до этого — публикация только по ссылке для своих.
- **Персональные данные**: правило — **в студии и в её сервере не хранить ФИО, телефоны, адреса** клиентов. Поле
  «Клиент» в КП (`offer.customer`) и заметки замера (`measurement.notes`) сейчас свободные — добавить подсказку
  «без ФИО и адреса, только номер замера» и проверку на телефонные номера/e-mail при сохранении в облако (мягкий
  запрет с предупреждением). Локальный `localStorage` — на компьютере менеджера, ответственность цеха.

## 5. Интерфейс (следующие шаги по словам Макса)

- **Левая панель фрагментов как в Базисе**: перетаскиваемые заготовки «Антресоль», «Нижний модуль», «Ящики», «Полки»,
  «Стол», «Пенал», «Платяной» — сброс на сцену создаёт корпус рядом с выбранным (`appendModule`) или наполнение в
  секцию (`dropFilling` уже умеет shelf/drawer/rod/mesh/pantograph). База: `ModuleLibrary` + `presets`.
- **Окно параметров при добавлении наполнения**: после сброса «Ящики»/«Полки» открывать компактную панель поверх
  сцены (не модальное окно на весь экран): количество полок или ящиков, направляющие, ручка или push, зазор между
  ящиками, цвет фасадов — с живым обновлением модели, чтобы редактируемые ящики оставались на виду. Реализация:
  `drawerPreview` + плавающий `.inline-editor` рядом с секцией, закрытие по Esc/клику вне.
- **Редактирование каждой панели отдельно** (толщина, вылеты, свесы) — отложено: тяжелее в реализации; сначала
  параметры стола/царги/подстолья (сделано 07.09), затем общая система «переопределений» деталей.
