## Жёсткие правила

1. **Правила цеха (раздел 5 инструкции) не менять и не «улучшать».** Это стандарты моего
   производства: фальш-панель 16 мм только по стороне петель и только в зоне выкатного элемента;
   петли по высоте фасада 2/3/4/5 плюс одна при ширине > 450; цоколь 80; подсветка только в
   стойках, 3000 ₽/пог.м поверх наценки; раскрой без вращения деталей; цена = закупка × наценка.
   Если правило кажется неверным — сделай как написано и отдельно задай мне вопрос.
2. **Все числа — только через `CONST` в `constants.js` и каталоги.** Магические числа в коде
   запрещены. Новую константу добавляй с комментарием, откуда она, или с пометкой `TODO`.
3. **Вычисляемое не хранится.** В JSON проекта только решения пользователя. Добавил поле в
   модель — добавь дефолт в `newProject`/`newModule`/`newItem` и в `migrateProject`.
4. **Не переписывать на фреймворк, сборщик, TypeScript, модули.** Не добавлять сторонние
   библиотеки. Простота файлов важнее элегантности: проект поддерживается через ИИ-ассистентов.
5. **Не переименовывать** декоры Lamarty, id элементов Лемана, типы наполнения — на них
   ссылаются сохранённые проекты пользователей.
6. Расчётная логика живёт в `model.js` / `rules.js` / `pricing.js` / `nesting.js`.
   В `render.js` и `editor.js` — только отображение и события.
7. Любое изменение модели из интерфейса заканчивается вызовом `update()`.
8. Экранируй всё пользовательское при вставке в HTML (`esc()` уже есть).
9. Не трогать и не коммитить `server/.env`, `server/data.db*`.
10. После правки JS/CSS поднимай `?v=N` во всех тегах `editor.html`.

## Как работаем

**Формат каждой задачи:**
1. Сначала коротко: как ты понял задачу, какие файлы затронешь, какие есть риски и вопросы.
   Если вопрос блокирующий — задай его и остановись. Если нет — сформулируй допущение и продолжай.
2. Потом код. Правки давай так, чтобы я мог их применить без разбора:
   - для небольших изменений — блок «файл → найти строку/функцию → заменить на», с достаточным
     контекстом, чтобы место было однозначным;
   - для больших — полный текст функции или файла целиком с пометкой «заменить файл полностью».
   Никаких «…остальной код без изменений» внутри функции, которую ты меняешь.
3. В конце — как проверить руками: пошагово в браузере, что я должен увидеть. Плюс прогон
   регрессионного чеклиста из раздела 11.0 инструкции (перечисли пункты, которые могла задеть правка).
4. Предложи текст коммита в формате `feat vN: ...` / `fix: ...` / `docs: ...` латиницей.

**Что мне важно:** работающий результат, а не объяснения. Не пересказывай мне инструкцию,
не описывай очевидное, не предлагай альтернативные архитектуры. Если чего-то не знаешь о коде —
попроси конкретный файл, а не угадывай его содержимое. Если задача большая — разбей на шаги,
каждый шаг заканчивается рабочим состоянием, которое я могу проверить.

**Терминология** (чтобы понимать друг друга): модуль — отдельный корпус (нижний на цоколе или
верхний-антресоль); проём — внутреннее пространство модуля между боковинами, дном и крышей;
наполнение — полки, штанги, секции ящиков, сетка Лемана; фальш — панель 16 мм торцом на
боковину; секция ящиков — стопка из N ящиков одной высоты на одном типе направляющих;
техничка — требуемые внутренние ширина и глубина под фурнитуру; КИМ — коэффициент использования
материала в раскрое; КП — коммерческое предложение.
